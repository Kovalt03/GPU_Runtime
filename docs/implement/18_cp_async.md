# 18 — `[m5]` cp.async 구현 보고서

> 커밋: `0e9e05e` ISA·스케줄러 · `25be975` 청크 더블 버퍼 · `9c74c5e` 벤치 · `3f0fb2e` 문서

> Ampere 가 도입한 비동기 복사. **기전은 87% 를 벌고, 렌더러에서는 2% 를 번다.**
> 이 문서의 값어치는 그 둘이 왜 다른지에 있다.

## 만든 것

### opcode 둘 (31 → 33)

```
V_CP_ASYNC_SHARED_GLOBAL_F32   shared[reg[src1]] = global[reg[src0] + imm]
S_CP_ASYNC_WAIT                in-flight 복사가 imm 개 이하가 될 때까지
```

**스킴에 세 번째 메모리 동사가 생겼다.** `LD`/`ST` 는 한쪽 끝이 레지스터인 것이고,
복사는 **양쪽이 메모리**라 어느 쪽도 아니다. 공간이 둘 붙고 PTX
`cp.async.shared.global` 처럼 목적지를 먼저 쓴다. 다만 인코딩은 `src0` 에 **전역**
주소를 넣는다 — "과금되는 주소는 언제나 src0" 이 메모리 모델 전체가 딛는 규칙이고,
읽는 순서보다 그게 위다. 둘이 어긋나므로 양쪽에 다 적어뒀다.

`CLAUDE.md` 의 네이밍 규칙과 `MemoryOpcodesCarryAddressSpace` 를 같이 넓혔다.

### 가장 미묘했던 결정 — 복사는 언제 큐에서 나가나

처음엔 **시간**으로 은퇴시켰다. `ready_at <= now` 면 없앴다. 그러면
`LatencyModel::Ignored` 에서 지연이 0 이라 **대기를 빼먹은 커널이 통과한다.**

PTX 도 선을 그렇게 안 긋는다. `cp.async.wait_group` 이 가시성을 만들지, 시간이
지났다고 보이는 게 아니다. 그래서 **대기로만** 나가게 고쳤다:

```
시간   워프가 언제 다시 발행할 수 있나        →  ready_at
대기   바이트를 언제 읽어도 되나              →  큐에서 제거
```

그 위에 **가드**를 얹었다. 아직 날아오는 목적지를 읽으면 던진다. 하드웨어는 그
자리에 있던 값을 주고, 그러면 커널이 **운으로 테스트를 통과한다.** 목적지 바이트
범위로 판정하므로 더블 버퍼링(기다린 절반을 읽는 것)은 안 걸린다.

큐가 꽉 차면 워프가 멈춘다 (`CP_ASYNC_QUEUE_DEPTH = 8`). 그 자리에서만 시간으로
슬롯을 회수한다 — 하드웨어도 그렇게 회수하고, 그때는 실제로 도착해 있다.

### 같이 드러난 버그

`Handback` 이 정상 종료 시 해제되고 있어서, **진행 불가로 루프를 빠져나올 때
블록이 호출자에게 안 돌아갔다.** 큐가 찬 워프를 park 시키자 SEGFAULT 로 나왔다.
항상 무장한 채로 두고, park 한 워프가 `soonest` 에 반영되게 고쳤다.

## `[m5b]` 청크 + 더블 버퍼

한 방 채우기만으로는 잴 것이 거의 없다 — 채우기가 한 번이고 walk 이 그걸 수천 번
읽는다. **채우기가 반복돼야** 값이 생기고, 그 경우를 지금까지 코드가 거부하고
있었다:

> "실제 하드웨어는 타일을 여러 패스로 쪼갠다. 여기서 그러려면 fill·barrier·walk 가
> 패스마다 반복돼야 하고, 그건 다른 커널이다"

그 "다른 커널" 을 `TileStaging::AsyncDoubleBuffered` 로 만들었다.

```
prologue:  청크 0 의 복사를 발행
loop:      다음 청크가 있으면 → 발행하고 cp_async_wait(K)      (없으면 wait(0))
           barrier
           이번 청크를 walk                                     ← 다음 청크는 날아오는 중
           barrier                                              (두 칸 뒤에 이 버퍼를 덮으므로)
```

**청크 크기가 64 삼각형인 이유가 대기 명령의 모양이다.** `S_CP_ASYNC_WAIT` 는
**개수**를 받으므로 커널이 "한 청크가 복사 몇 개인지" 를 빌드 시점에 알아야 한다.
64 × 12 = 768 float 이고 블록이 256 스레드라 **정확히 워프당 3 개**다. 회전 루프로
발행하면 그 수가 타일마다 달라지고, "직전 청크만큼" 을 기다리는 명령은 없다.

꼬리는 **소스 주소를 클램프**해서 채운다. 마지막 청크가 모자라면 이미 있는 float 을
다시 실어오고, walk 은 존재하는 삼각형만 도므로 읽히지 않는다.

**덤으로 341 삼각형 제한이 사라졌다.** 그 제한은 경로의 성질이 아니라 **한 패스로
채우는 것의 성질**이었다.

---

## 나온 것

### ① 기전 — 채우기만 떼어놓고

| float | sync 사이클 | async 사이클 | |
|---:|---:|---:|---|
| 8 | 3,250 | 449 | **-86.2%** |
| 64 | 25,930 | 3,249 | **-87.5%** |

발행량도 -65% (공유 스토어가 통째로 사라진다).

**사이클이 큐 깊이만큼 준다.** 8 개를 띄워두니 메모리 왕복 여덟 개가 겹친다 —
1/8 = 87.5%, 마지막 행이 그 숫자다. **상수가 측정으로 회수됐다.**

### ② 렌더러 — 같은 기전, 2%

| 씬 | 삼각형 | sync 사이클 | async 사이클 | |
|---|---:|---:|---:|---|
| small, spread | 16 | 19,500 | 19,976 | **+2.4%** |
| full-frame | 64 | 335,258 | 330,398 | -1.4% |
| full-frame | 128 | 524,954 | 515,678 | **-1.8%** |

**87% 가 2% 가 된다.** 프레임은 동일하고 기전도 같다. 달라진 것은 **그 기전이 커널의
몇 %에 적용되는가**뿐이다.

### 왜 — 비율이 또 결정한다

```
스테이징한 float 하나 :  가져오기 1 번,  읽기 256 번   (블록의 스레드 수)
```

타일의 모든 픽셀이 타일의 모든 삼각형을 도므로, 가져오기를 통째로 숨겨도 **walk 의
1/256** 이 상한이다. **씬이 못 바꾼다 — 커널의 성질이다.** 삼각형이 늘수록 이득이
커지는 건 청크가 늘어 겹칠 기회가 늘기 때문이고, 그 상한으로 수렴한다.

`[e]` 의 `2/(1+s/c)` 와 같은 종류의 결론이다. **이 프로젝트에서 최적화의 값을
결정한 것은 세 번 다 비율이었다.**

### 작은 씬은 진다

청크가 64 삼각형이라 16 삼각형짜리 타일은 **필요한 것의 네 배**를 싣는다. 발행량
+12.6%. 그게 **빌드 시점에 알 수 있는 대기 개수의 값**이다 — 회전 루프였다면 대기를
표현할 수 없었다.

### 이길 자리는 어디였나

교환은 **가져오기 대 재사용**이고 이 커널은 반대쪽 끝이다(1 대 256). `cp.async` 가
도입된 자리는 **행렬 곱의 안쪽 루프** — 타일 하나를 정해진 소수의 MAC 으로 소비하니
가져오기가 진짜 비중이고 더블 버퍼가 그걸 덮는다. 그게 `[m6]` 이고, 이 명령은
거기서 다시 재게 된다.

---

## 검증

- `ctest` **307/307** — 스케줄러 7 개, 파이프라인 2 개 신규
- **프레임 동일** — 청크 더블 버퍼가 한 방 채우기와 픽셀 단위로 같다
- **가드가 잡는다** — 대기 없이 읽으면 던지고, 안 걸리는 절반은 안 걸린다
- **큐가 차면 멈춘다** — 깊이보다 많이 발행해도 전부 나가고, 대기가 큐를 비운다
- **제한이 사라졌다** — 341 을 넘는 타일이 async 에서 돈다
