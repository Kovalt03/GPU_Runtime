# 13 — 지연·coalescing 구현 보고서

지금까지 중 가장 큰 작업이고, 유일하게 **기존 측정치를 전부 무효로 만드는**
작업이다. `DOC/12` 이 `[m1]`·`[m2]` 에 대해 그랬듯 "어떻게" 를 적는다.

---

## 무엇을 진짜로 구현하고 무엇을 세기만 하나

이 프로젝트에서 반복해서 갈리는 지점이라 여기 적어 둔다.

```
값이 달라지는 것          진짜로 구현해야 한다
언제/얼마나만 달라지는 것  세기만 하면 된다
```

**coalescing 은 세기만 한다.** 하드웨어가 32 개 요청을 합치지만, 합쳐도 **읽어
오는 값이 같다.** `execute()` 는 여전히 레인마다 `load_f32` 를 부르고, 옆에서
라인 수만 센다. 합치는 코드를 써도 관찰 가능한 차이는 비용 숫자뿐이다.

**캐시도 세기만 한다.** 필요한 것은 **태그와 LRU 순서**뿐이고 데이터 배열이
아니다 — 값은 `DeviceSpan` 에 있고 캐시에 복사해도 같은 값이 나온다. 상주 라인
집합과 최근성만 있으면 히트·미스가 갈리고, 그것이 비용과 지연의 전부다.

과거 이력도 필요 없다. LRU 순서는 **축출 대상을 고르기 위한 현재 상태**이고,
"언제 들어왔는지" 를 기록해 둘 이유는 없다.

이건 편법이 아니라 타이밍 모델 캐시 시뮬레이터의 표준 형태다 — cachegrind 도,
gpgpu-sim 의 캐시 모델도 태그만 쓴다.

**데이터가 필요해지는 것은 일관성을 모델링할 때다.** write-back 캐시에서 더티
라인이 안 내려간 사이 다른 주체가 옛 값을 읽는 상황. 이 기계엔 없다 — 블록 안은
`BARRIER` 가, 블록 사이는 순차 실행이 순서를 잡는다. write-back 을 넣어도
필요한 것은 **라인당 더티 비트 하나**이고 여전히 데이터가 아니다.

**반대쪽 예가 `V_SHUFFLE_F32` 다.** 값이 실제로 레인 사이를 건너야 하므로 진짜
구현이 필요했고, 그래서 읽기-쓰기 순서 버그가 났다. 세기만 하는 것에는 그런
버그가 없다.

**`[m4]` 는 다시 갈릴 자리다.** 비동기 런치가 "여러 블록이 겹쳐 돈다" 는 뜻이면
블록들의 상태가 동시에 살아 있어야 하고, 그러면 세는 것으로 안 된다. 순서만
바꾸는 것인지 실제로 겹치는 것인지를 그때 먼저 정할 것.

## 왜 캐시와 지연을 묶나

**같은 숫자를 두 번 정하지 않기 위해서다.** 캐시 히트와 미스는 비용만 다른 것이
아니라 **지연이 자릿수로 다르다** — 하드웨어에서 L1 은 수십 사이클, L2 는 수백,
DRAM 은 그 위다.

캐시를 먼저 넣고 지연을 나중에 하면 라인 비용을 한 번 정하고, 지연을 넣을 때
"그 비용이 실은 어디서 왔는지" 를 다시 정하게 된다. 반대로 지연을 먼저 넣으면
로드 지연을 하나로 정했다가 캐시가 들어오는 순간 갈라야 한다.

그리고 `RESULTS.md` 도 한 번만 다시 쓴다 — 초기 설계 기록 의 원칙 4 다.

```
지금        weighted = Σ(활성 레인 × instruction_cost)
coalesced   글로벌 접근을 라인으로 센다                    ✅ 완료
cached      그 라인이 이미 있었는지 본다
latency     발행 슬롯과 결과 대기가 갈린다
```

## `[d]` coalescing — 완료

`global_access_cost()` 하나였다. 스케줄러 구조를 안 건드린다.

```cpp
uint64_t WarpScheduler::global_access_cost(const Warp& warp,
                                           const Instruction& instr) const
{
    const uint64_t lanes = active_lane_count(warp);
    if (memory_ == MemoryModel::Flat) {
        return lanes * instruction_cost(instr.op);
    }

    // 라인은 최대 32 개다 — 레인마다 하나씩. 정렬해서 세면 되고,
    // 32 개짜리에 set 을 쓸 이유는 없다.
    std::array<uint64_t, WARP_SIZE> lines{};
    uint32_t n = 0;
    for (uint32_t lane = 0; lane < WARP_SIZE; ++lane) {
        if (!is_active(warp, lane)) continue;
        const float byte = warp.threads[lane].regs[instr.src0] + instr.imm;
        // decode_address 가 이미 정렬·범위를 본다. 같은 검사를 두 번 하지 말 것
        lines[n++] = decode_address(byte, "...") / CACHE_LINE_BYTES;
    }
    std::sort(lines.begin(), lines.begin() + n);
    const uint32_t distinct = std::unique(lines.begin(), lines.begin() + n)
                              - lines.begin();

    return distinct * instruction_cost(instr.op);
}
```

**라인당 `instruction_cost` 를 물린다**는 것이 핵심이다. 지금은 레인당 100 이라
워프 하나가 3200 을 낸다. 라인으로 세면 정렬된 접근이 **100**, 흩어진 접근이
**3200** — 32 배 차이가 처음으로 표현된다.

```
lane 0..31 이 &buf[lane]      → 128 바이트 한 라인   → 100
lane 0..31 이 &buf[lane * 32] → 32 개 라인          → 3200
lane 0..31 이 &buf[0]         → 한 라인 (브로드캐스트) → 100
```

`CACHE_LINE_BYTES` 는 128 로 뒀다 — NVIDIA 가 워프 하나에 옮기는 크기이고,
4 바이트 float 이면 워프 32 레인이 정확히 한 라인이다. **정렬된 연속 접근이 1,
완전히 흩어진 접근이 32.**

### 정할 것 셋

**① 저장은 적재와 다르다.** 라인 전체를 채우는 쓰기는 먼저 읽을 필요가 없고,
일부만 건드리는 쓰기는 읽어야 한다. 똑같이 물리면 간단하지만 말해 주는 것이 적다.

**② 주소를 두 번 계산할 것인가.** `execute()` 가 이미 레인마다 같은 식을
계산한다. 여기서 다시 모으면 두 번 계산이고, `execute()` 가 돌려주게 하면 빠른
대신 주소 산술이 두 군데가 된다.

**③ 공유 메모리도 셀 것인가.** 실제 하드웨어에서 LDS 는 캐시 라인이 아니라
**뱅크 충돌**로 비용이 갈린다 — 32 뱅크에 레인 32 개가 서로 다른 뱅크를 짚으면
한 번, 같은 뱅크를 짚으면 직렬화된다. 다른 모델이므로 `[d]` 의 첫 판에는 넣지
않는 편이 낫다. 다만 `MemoryModel` 이름이 글로벌만 뜻하지 않도록 주의할 것.

### 무엇이 드러났나

**전 경로에서 약 93% 가 빠졌고 전부 한 가지 이유다.** 커널들이 삼각형을 워프
균일하게 읽는다 — 32 레인이 같은 주소를 대므로 라인 하나다. 고정 모델이 그것을
로드 32 개로 물리고 있었다.

```
walk      31,317,520 → 2,210,320   -92.9%
tiled     11,311,632 →   854,032   -92.4%
shared     2,354,064 → 1,383,664   -41.2%
raytrace  23,656,822 → 1,692,022   -92.8%
```

**공유 메모리 스테이징이 뒤집혔다.** 타일드 대비 고정 모델에서 79% 이겼는데
여기서는 62% 진다. 스테이징은 "32 레인이 같은 글로벌 로드를 각각 내는 것" 을
막으려고 존재하는데, **그 로드가 어차피 라인 하나였다.** 아낄 것이 없는데 공유
store·load·배리어는 그대로 냈다.

`RESULTS.md` 가 "공유 메모리가 버는 95% 는 100 대 8 의 산술이지 캐시 이야기가
아니다" 라고 적어 놨었다. 검증된 것이 아니라 **결론이 뒤집혔다.**

`shared` 만 -41% 인 것도 같은 이유다 — 글로벌 로드 비중이 이미 낮아 깎일 것이
적었다.

### 그래서 최적화 여지가 어디 남았나

**지금 커널에는 별로 없다.** 이미 브로드캐스트라 라인 하나다. 흩어진 접근을
찾아야 하고, 후보는 **인덱스 버퍼**다 — 삼각형마다 인덱스 셋을 읽고 그것이
가리키는 정점을 읽는데, 정점이 메모리에서 흩어져 있으면 라인이 여럿이다.

**`[9d]` Forsyth 재정렬이 0.004% 밖에 못 벌었던 것**이 여기서 다시 볼 거리다.
캐시 지역성이 그 재정렬의 원래 목적인데, 그때는 지역성을 표현할 모델이 없었다.

`V_LD_GLOBAL_VEC3_F32` 도 여기 걸린다. 지금 정점 하나를 float 4 개로 나눠 읽는데
한 명령어로 읽으면 라인 수가 줄어드나 — 재 봐야 안다. **둘 다 캐시가 들어온
뒤**가 맞다. 지금 재면 재정렬의 값을 절반만 본다.

## `[d]` 메모리 계층

`MemoryModel::Cached`. `Coalesced` 가 "라인 몇 개를 건드리나" 라면 이쪽은
"그 라인이 이미 있었나" 다.

**왜 필요한가.** 트랜잭션을 세는 것은 반복을 말해 주지 않는다. naive walk 의
**모든 워프가 같은 삼각형을 다시 읽는다.** `Coalesced` 아래서 워프마다 라인
값을 온전히 낸다 — 바로 앞 워프가 만진 라인인데도. 캐시가 그 두 번째 읽기를
싸게 만드는 것이고, 그것이 walk 와 tiled 의 차이를 다시 정할 수 있다.

### 정할 것 둘

**① 상태를 누가 갖나 — 저절로 풀렸다.** L1 은 블록 하나의 것이므로 `run()`
머리에서 비운다. L2 는 장치의 것이고 런치보다 오래 살아야 하는데,
`MyGPURuntime` 이 생성자에서 스케줄러를 **한 번** 만들고 런치마다 재사용하므로
**스케줄러 멤버로 두면 수명이 정확히 맞는다.** `run()` 의 시그니처를 바꿀 필요가
없었다.

**② 어떤 축출을 모델링하나.** 상주 라인 집합 + LRU 로 갔다. set·way 까지 가면
더 말하지만 **라인→set 사상이 맞아야** 하고, 틀리면 더 말하는 것이 아니라 틀린
것을 말한다.

**자료 구조는 map + list 다.** 태그만 담으므로 `unordered_map<size_t,
list<size_t>::iterator>` 이고 값은 라인 번호와 그 LRU 위치뿐 — 데이터가 아니다.
선형 스캔이 아닌 이유는 L2 가 수만 라인이고 조회가 수백만 번이라서다.

### 크기와 지연

```
L1   1024 라인 = 128 KB      Volta 이후 SM 당 정확히 이 값
L2  65536 라인 =   8 MB      세대마다 다르다. V100 6 MB, A100 40 MB
```

**L1 은 정확하고 L2 는 자리표시자다.** 이 규모의 씬은 L2 의 30 분의 1 도 못
채운다 — 채우려면 화면 데이터로 약 175,000 삼각형이 필요하다. 그래서 **어느
테스트도 L2 축출을 건드리지 못하고**, 크기를 바꿔도 아무 수치가 안 움직인다.

여기서 L2 가 실제로 하는 일은 **L1 이 버린 것을 받는 것**이고 그건 검증된다.
L2 도 결국 버린다는 것은 검증되지 않는다. 그 구분을 적어 둔다.

비용도 측정이 아니라 모델링 선택이다 — `instruction_cost` 와 같은 출처다.

```
L1 히트     8    공유 로드와 같은 급
L2 히트    30
미스      100    글로벌 로드의 원래 값
```

### 무엇이 나왔나

**하드웨어 크기에서는 캐시가 곡선이 아니라 상수 −40% 를 번다.**

```
tris     coalesced        cached    change   hit rate
 360    62,432,720    37,136,442    -40.5%     99.9%
10000 1,730,694,480 1,029,364,282  -40.5%    100.0%
```

작업 집합이 27 배 커져도 같다. **패스 1 의 스토어가 화면 버퍼 전체를 L2 에 올려
놓고**(3,750 라인 ≪ 65,536) 패스 2 가 전부 거기서 찾는다. 이 규모에서 L2 는
사실상 무한하다.

**축소 캐시(L1 32 / L2 512, 하드웨어가 아님)에서 무릎이 나오고, walk 에서만 나온다.**

```
tris   route   scene/L2   hit rate     misses
1000    walk      0.73x     100.0%        383
3000    walk      2.20x      96.9%     72,318   ← 여기
3000   tiled      2.20x      99.5%      1,398   ← 안 넘긴다
```

**그래서 비닝은 작업량 최적화만이 아니라 지역성 최적화다.** walk 의 블록 하나는
모든 삼각형을 읽으므로 작업 집합이 씬 전체이고, tiled 의 블록은 자기 타일 목록만
읽으므로 그 몇 분의 일이다. 고정 비용 모델은 비닝의 이득을 전부 "삼각형을 버려서"
로 설명했는데 **그중 일부가 지역성이었다.**

**`shared` 의 히트율이 65~70% 로 혼자 낮다** — 조회 자체가 240 배 적다. 글로벌
재읽기를 없앤 경로가 캐시에서 얻는 것이 가장 적다는, 일관된 이야기다.

**비용 변화는 +1.6% 뿐이다.** 미스가 190 배 늘어도 여전히 소수다. 무릎은 히트율과
미스 수에서 보이고 총비용에서는 거의 안 보인다.

### 아직 안 보이는 것 — 용량 미스

**여러 씬을 이어 그려도 안 나온다.** 24 draw 를 이어 돌려도 히트율이 99.4% 로
평평하다. 각 draw 가 자기 데이터만 읽으므로 **이전 draw 의 데이터가 밀려나도 다시
읽지 않아 보이지 않는다.** 미스는 그 draw 몫의 강제 미스이고 캐시 크기와 무관하다.

**같은 지오메트리를 다시 그려도 안 나온다.** `draw_*` 가 호출마다 새로 할당하고
해제하지 않으므로, 두 번째가 다른 주소에 올라간다 — 재방문이 아니라 또 강제 미스다.

**그래서 이것은 캐시가 아니라 API 의 공백이다.** "한 번 올리고 여러 번 그린다" 를
표현할 방법이 없다. 초기 설계 기록 의 `[b]` 가 그것이고, `[e]` early-Z 의 선행 조건이다.

## 지연과 캐시가 만나는 지점

**`instruction_latency(Opcode)` 는 글로벌 로드에 답할 수 없다.** 시그니처가 opcode
만 받는데, 로드의 지연은 **라인이 어디서 발견됐는지**에 달렸다.

인과를 뒤집어 생각하기 쉽다. 고정된 시간을 기다린 뒤 캐시를 보는 것이 아니다 —
**찾은 위치가 곧 기다린 시간**이다. 순차로 일어나는 두 사건이 아니고, 한 사건의
소요 시간을 조회 결과가 정한다.

그래서 "따로 측정할 수 없다" 는 틀린 표현이다. **따로 두는 것은 되고, 다만 지연을
계산하는 쪽이 조회 결과를 받아야 한다.**

### 진짜 제약은 조회의 부작용이다

```cpp
bool LineCache::touch(size_t line)   // LRU 순서를 바꾸고, 없으면 설치한다
```

비용 때문에 한 번, 지연 때문에 또 한 번 조회하면 **설치가 두 번 되고 LRU 가
망가진다.** 두 번째는 첫 번째가 넣어놨으므로 무조건 히트다.

부작용 없는 `peek()` 를 따로 두는 것도 되지만, **두 답이 일치한다는 보장을 사람이
지켜야 한다.** 한 번의 조회에서 둘을 받는 쪽이 그 부담이 없다.

### 어디에 두나

`instruction_latency` 는 **opcode 로 정해지는 것만** 답하고 그대로 둔다. 글로벌
접근의 예외는 **상태가 있는 쪽**, 즉 스케줄러가 다룬다.

`global_access_cost` 가 이미 그 예외를 다루는 함수다. 지금 비용만 반환하는 것을
비용과 지연 둘로 바꾸면 되고, `step_warp` 이 이미 그 갈래를 갖고 있으므로 **새
분기가 생기지 않는다.**

```cpp
const bool touches_global = ...;
stats_.weighted_lane_ops += touches_global ? global_access_cost(...) : lanes * cost;
//                                           ^^^^^^^^^^^^^^^^^^^^^ 여기서 지연도 받는다
```

### 네 칸을 다 채워야 한다

두 축이 독립이라 조합이 넷이다.

```
Flat      + Ignored     아무것도 안 기다림, 레인 단위 비용     ← 지금
Coalesced + Ignored     아무것도 안 기다림, 라인 단위 비용     ← 지금
Cached    + Ignored     아무것도 안 기다림, 캐시 반영 비용     ← 지금
Flat      + Modelled    로드 지연이 고정값 하나              ← 새로 정할 것
Cached    + Modelled    조회가 비용과 지연을 함께 정함        ← 흥미로운 칸
```

`Flat + Modelled` 는 조회할 캐시가 없으므로 고정값을 쓴다. 그리고 그 칸이 **비교
기준**으로 쓸모가 있다 — "캐시 없이 지연만" 과 "둘 다" 를 비교하면 캐시가 **시간에서**
버는 몫이 비용에서 버는 몫과 따로 나온다.

### 다른 opcode 는

지금은 로드뿐이고, 조건부인 것이 둘 있다.

**스토어** 는 하드웨어에서 대체로 fire-and-forget 이다 — 쓰기 버퍼에 넣고 워프는 안
기다린다. **워프가 스토어 완료를 기다리게 모델링할지** 를 정하면 충돌 여부가
결정된다. 안 기다리면 지연이 0 이라 충돌이 없고, 비용만 라인 수에 달린다.

**공유 메모리 로드** 는 지금 고정이다. 하드웨어에서는 **뱅크 충돌**로 갈리는데
`[d]` 가 명시적으로 범위 밖에 뒀다. 넣으면 똑같은 종류의 문제가 생긴다.

`BARRIER` 와 `S_SYNCWARP` 은 해당이 없다 — 결과 지연이 아니라 대기 자체이고
스케줄러가 직접 모델링한다.

## `[m3]` latency / occupancy — 구조가 바뀐다

`run()` 이 지금은 큐에서 워프를 꺼내 **무조건** 한 스텝 돌린다. 지연이 생기면
"돌릴 수 있는 워프" 와 "기다리는 워프" 가 갈린다.

```cpp
// 지금 — 큐에서 꺼내면 무조건 돈다
while (!ready_queue_.empty()) { pop; step_warp; push; }

// 필요한 것
uint64_t now = 0;
while (아직 살아있는 워프가 있다) {
    Warp* w = now 시점에 ready_at <= now 인 워프 중 하나;   // 라운드로빈
    if (!w) {
        // 전부 대기 중. 시간을 가장 빠른 ready_at 으로 건너뛴다
        stats_.stall_steps += 1;
        now = 남은 워프들의 ready_at 최솟값;
        continue;
    }
    step_warp(...);
    w->ready_at = now + instruction_latency(발행한 opcode);
    now += 1;                       // 발행 슬롯 하나
}
```

`Warp::ready_at` 은 이미 있고 `run()` 이 0 으로 초기화한다. **레지스터 단위
스코어보드까지 갈 필요가 없다** — 이 기계는 한 워프가 한 번에 명령어 하나만
발행하므로, 다음 명령어가 앞 결과에 의존하든 말든 어차피 기다린다. 보수적이지만
occupancy 가 드러나는 데는 충분하고, 정확한 의존성 추적은 `[m3]` 이 답하려는
질문이 아니다.

`run_modelled()` 가 `run()` 옆에 서 있다. **안에 넣지 않은 이유**는 둘이 루프의
형태에서 갈리기 때문이다 — 한 분기가 아니다. 레이 트레이서의 프리디케이션과 같은
순서로 간다: 따로 짓고, 재서 비교한 뒤에 합친다.

### 이 모델이 보일 수 있는 occupancy 는 블록 안뿐이다

**가장 큰 제약이고, 구현 전에 알아야 한다.**

하드웨어에서 occupancy 는 "SM 에 상주한 워프가 지연을 가릴 만큼 많은가" 이고, 그
워프들은 **여러 블록에서 온다.** 여기서는 `myrt_launch` 가 블록을 하나씩 끝까지
돌리고, `run()` 이 블록마다 시계를 0 에서 시작한다.

```
하드웨어    SM 하나에 블록 여럿이 상주하고, 그 워프 전부가 서로를 가린다
여기        블록 하나가 끝나야 다음이 시작한다. 가릴 수 있는 것은 그 블록의 워프뿐
```

블록이 최대 32 워프(1024 스레드)이므로 그 범위 안에서는 제대로 보인다 — 워프 1 개와
8 개의 차이가 드러나고, 그것이 `[m3]` 의 벤치마크다. 하지만 **"블록을 더 많이
띄워 가린다" 는 표현되지 않는다.** 그것은 `[m4]` 다.

`README` 의 "What this models" 에 이 구분을 적을 것 — "latency hiding: modelled
within a block" 이지 그냥 modelled 가 아니다.

### 정해진 것 넷

**① 준비된 워프 중 라운드로빈.** 하드웨어는 greedy-then-oldest 계열이지만, 지금
스케줄러의 공정성을 유지하는 쪽을 택했다.

**이 선택이 검증 하나를 공짜로 준다.** 지연을 전부 0 으로 두면 어떤 워프도 기다리지
않으므로 라운드로빈이 `Ignored` 와 **같은 순서로 발행한다.** 그러면 두 모델의 통계가
바이트 단위로 같아야 하고, 그것이 사이클 루프가 기존 루프를 정확히 재현하는지 보는
시험이 된다. `[m1]` 에서 정책 전환이 측정치를 안 흔든 것을 확인한 것과 같은 방법이다.

**② `stall_steps` 는 건너뛴 사이클 수.** "몇 번 막혔나" 가 아니라 "얼마나 오래
막혔나" 다. 100 사이클 한 번과 1 사이클 백 번이 구별되고, occupancy 를 올리면 이 값이
줄어드는 것이 보인다.

**③ 스토어는 기다리지 않는다.** 하드웨어의 fire-and-forget 과 같다 — 쓰기 버퍼에
넣고 진행한다. 지연이 0 이므로 캐시와 충돌하지 않고, 비용만 라인 수에 달린다. 쓰기
버퍼가 가득 차는 경우는 흉내 내지 않는다.

**④ 기존 예산이 사이클도 센다.** 상한 하나로 발행과 정지를 합쳐 세므로 영원히
기다리는 블록이 반드시 걸린다. `[m1]` 의 교착 테스트가 그 예산에 기대고 있어 이것이
빠지면 그 테스트가 무한 루프가 된다.

**이름을 고쳐야 한다.** `step_budget_` / `DEFAULT_STEP_BUDGET` / `set_step_budget`
이 이제 사이클까지 뜻하므로, 스텝만 센다고 읽히는 이름을 그대로 두면 안 된다.

### 아직 정하지 않은 것

**배리어의 도착 판정.** `release_barrier` 는 **큐가 마르면** 풀어 주고 그것이 판정
전부다. 시계 기반 루프에는 그런 큐가 없다.

여기에는 제약이 하나 있어서 선택지가 좁다: "준비된 워프가 없다" 만으로 풀어 주면
**전부 지연 대기 중일 때도 배리어가 열린다.** 판정은 "**앞으로 어떤 살아 있는 워프도
풀어 주지 않고는 발행할 수 없다**" 여야 하고, 그것은 지연 대기 중인 워프가 하나도
없을 때다. 즉 시간을 먼저 건너뛰고, 그래도 발행할 워프가 없을 때 배리어를 본다.

**지연 값 자체.** `instruction_latency` 가 여전히 0 이다. 비율은 `gpurt/isa.cpp` 주석에
적혀 있고, `Flat + Modelled` 에서 쓸 글로벌 로드의 고정값도 함께 정할 것.

`step_warp` 이 `warp.pc` 에 **발행한 명령어의 pc** 를 남기므로, 지연은 호출 뒤
`instruction_latency(program[warp.pc].op)` 로 얻는다. 시그니처를 바꿀 필요가 없다.

### 걸릴 것 셋 더

**① 스텝 예산이 정지 사이클을 덮어야 한다.** 지금 예산은 **발행한 스텝**을 센다.
정지가 예산에 안 잡히면, 영원히 기다리는 블록이 발행을 안 하므로 **예산이 늘지 않고
멈춘다.** `[m1]` 의 교착 테스트가 예산에 기대고 있으므로 이것이 깨지면 그 테스트가
무한 루프가 된다. 사이클도 세거나, 사이클 상한을 따로 둘 것.

**② 살아 있음과 준비됨이 다르다.** 지금 `run()` 은 큐에 있으면 돌리고 `step_warp`
이 false 를 돌려주면 안 넣는다 — 큐 자체가 "살아 있는 워프 목록" 이다. 시계가 생기면
**"살아 있지만 아직 준비 안 된 워프"** 가 생기므로 둘을 따로 알아야 한다.

**③ 배리어가 큐 밖에 있다.** `release_barrier` 는 **큐가 마르면** 풀어 준다 — 그것이
도착 판정이다. 시계 기반 루프에는 그런 큐가 없으므로 판정을 다시 만들어야 한다.
"준비된 워프가 없다" 가 전부 지연 대기인 경우와 전부 배리어 대기인 경우로 갈리고,
앞은 시간을 건너뛰고 뒤는 풀어 준다.

### 잃는 것 — `warp_steps` 의 의미

지금 `warp_steps` 는 "발행한 명령어 수" 이고 흘러간 시간과 같다. 지연이 들어오면
갈라진다.

```
warp_steps        발행한 명령어 수        발산이 낭비하는 것
now (사이클)       흘러간 시간            지연이 낭비하는 것
stall_steps       아무도 못 돈 사이클     occupancy 가 줄이는 것
```

**`divergence_rate` 의 분모를 다시 정해야 한다.** 지금은 `warp_steps × 32` 다.
그대로 두면 발산율은 지금 뜻 그대로 유지되고(발행 슬롯 중 마스크된 비율), 시간을
분모로 바꾸면 "지연 때문에 논 것" 까지 발산으로 잡힌다. **전자를 권한다** — 둘은
다른 낭비이고, 섞으면 어느 쪽을 고쳐야 하는지 말해 주지 못한다. 대신 `stall_steps`
로 두 번째 낭비를 따로 보고한다.

### 무엇이 드러났나

```
warps    steps   cycles   stalls   cyc/warp
    1        6       30       24     30.0
   16       96       96        0      6.0
```

**워프당 사이클 30 → 6, 16 워프에서 정지 0.** 산술 지연(4~16)은 블록 하나로 완전히
가려진다.

**글로벌 로드(400)는 32 워프로도 못 가린다.** 블록 최대가 32 워프이고 각자 몇
사이클씩인데 상대가 수백 사이클이므로, 채워도 **사라지지 않고 퍼지기만** 한다.
occupancy 가 충분한지는 **무엇을 가리는지에 달렸다** 는 것이 결과다.

**캐시가 시간에서도 이긴다.** 32 워프에서 `Flat` 496 사이클 대 `Cached` 437 —
첫 워프가 미스하고 나머지가 L1 히트다. 지금까지 캐시는 발행 비용만 아꼈다.

### 설계 결정 하나가 씬을 필요로 했다

**비용은 라인마다 더하고 지연은 최댓값을 쓴다.** 라인들이 함께 페치되므로 워프는
가장 느린 것을 기다린다. 이 규칙이 처음엔 안 잡혔는데 **기존 씬이 전부
브로드캐스트(라인 하나)** 라 합과 최댓값이 같은 값이었다.

### 워프를 묶는 이유 자체 지금은 블록에 워프가 몇 개든 총량이 정확히 비례한다
(reduction_bench 에서 68 → 136 → 272 → 544 로 확인). 지연이 생기면 **그 비례가
깨져야 한다** — 워프 하나면 로드마다 통째로 서고, 여덟이면 서로 가려 준다.

이것이 `[m3]` 의 벤치마크다. 같은 커널을 워프 1·2·4·8 로 돌리고 **워프당 시간**을
본다. 지금은 평평하다. 지연이 들어오면 내려가야 하고, 어디서 평평해지는지가
그 커널의 occupancy 요구다.

`[m4]` 비동기가 "흉내만 낸다" 던 것도 여기서 풀린다. 겹칠 것이 생기기 때문이다.

사이클은 캐시와 함께 -42.9%, 캐시 없이 -64.9%. 캐시가 이미 발행 쪽 이득의 대부분을
먹고 있었다(-3.1%) — 2·3 번째 스칼라 로드가 L1 히트 8 이었으니까. 캐시가 못 먹는 것은
**기다림**이다: 스코어보드가 없어 로드 하나가 한 번의 대기다.

**7 의 Forsyth 회수분.** L1 이 메시보다 작을 때 인덱스 walk 의 사이클 24.7%,
발행 용량 1.6%. 미스는 226 으로 양쪽 같다 — 전부 compulsory 이고 움직이는 것은
"어느 계층이 답했나" 뿐이다. 창은 메시 크기가 정한다: 라인당 정점 8 개이므로
하드웨어 L1(1024 라인)에 닿으려면 정점 8,192 개가 넘어야 하고, walk 이
O(픽셀×삼각형) 이라 그 크기는 벤치가 감당하지 못한다. 그래서 축소한 L1 로 재고,
축소했다는 것을 표에 적는다. 통제군은 tiled — `bin_triangles` 가 호스트에서
de-index 하므로 순서가 캐시에 닿지 않고, ±0.1% 로 나온다.

**2 와 3 을 한 커밋으로.** 캐시 히트와 미스의 지연이 자릿수로 다르므로 따로 하면
그 숫자를 두 번 정한다.

**7 이 있어야 끝난 것으로 친다.** 자를 고치는 작업은 그 자로만 보이는 결과를
하나 내야 값을 한다. `[m1]` 이 그러지 못한 상태로 남아 있다 — 교착을 풀었는데
측정치가 하나도 안 움직였다.

**4 번이 진짜 결과다.** 표 두 벌을 나란히 두는 것보다 "비용 모델을 바꿨더니 어떤
최적화의 순위가 바뀌더라" 한 문장이 더 말한다.

`RESULTS.md` 의 "What is measured" 절에 **"이 파일의 수치는 모두 현재 모델에서
나왔고, 지연과 coalescing 이전 모델의 수치는 `67183c0` 에 있다"** 를 적는다.

### 뒤집힐 만한 것들

미리 적어 두되 **예측이지 결과가 아니라는 것을 잊지 않는다.** 이 프로젝트에서
재기 전에 쓴 주장은 지금까지 네 번 다 틀렸다.

- 프리디케이션이 지금 2~4.4% 진다. 발산의 비용이 커지면 뒤집힐 수 있다
  → **틀렸다. 반대로 훨씬 크게 진다** — 라인 과금 +19~75%, 캐시 +32~93%,
  사이클 +15~46%. 평탄 모델이 로드를 레인당 100 으로 매겨 블렌드가 더 하는
  산술을 덮어주고 있었다. 발산은 여전히 정확히 0.00% 로 사라진다
- 공유 메모리 스테이징의 96% 는 100 대 8 의 산술이다. coalescing 이 들어오면
  달라진다 → **맞았고, 그 이상이었다.** 이득 자체가 사라졌다 (+62%)
- 인덱스 버퍼가 패스 2 에 24% 를 물린다. 그 세 번의 dependent load 는 지연이
  생기면 지금보다 훨씬 비싸진다
  → **틀렸다. 절반으로 줄었다** — 캐시 +12.8%, 사이클 +16.2%. 인덱스 로드가
  워프 균일이라(32 레인이 같은 삼각형의 같은 인덱스를 읽는다) 평탄 모델이 32 배
  과대 계상하고 있었다

**정적 감사로 확인한 것.** 예측과 반대로 나왔으니 모델 버그부터 의심했고, 아니었다.
결정적 증거는 **프리디케이션의 절대 차이가 세 모델에서 완전히 같다**는 것이다 —
walk 816,544 / tiled 99,744 / raytrace 1,397,970. 블렌드가 더 하는 것이 전부 산술이라
(명령 스트림 감사: 산술 +10, 로드 +0) 메모리 모델이 건드릴 것이 없다. 퍼센트가 커진
것은 **분모가 93% 무너져서**다. 인덱스 쪽은 반대로 절대 차이가 20~45 배 줄어드는데,
그것이 "추가 로드가 워프 균일이었다" 의 정확한 서명이다.

**대신 다른 것 둘이 나왔다.** ① 비용 계산이 `execute()` **뒤**에 주소 레지스터를 읽고
있었다 — `V_LD_GLOBAL_F32 r0, [r0]` 같은 합법 프로그램이 방금 읽은 값을 주소로 쳐서
엉뚱한 라인을 물리거나 아예 던진다. ② `models.csv` 가 씬 이름의 쉼표를 안 감쌌다.
둘 다 고쳤고 회귀 테스트를 붙였다. 수치는 하나도 안 움직였다.

**그리고 모델의 한계 하나.** 스코어보드가 없어서 **의존을 구분하지 못한다** — 발행하면
무조건 지연만큼 기다리므로 종속 로드 사슬과 독립 로드 셋의 사이클이 같다. "dependent
load 가 지연에서 비싸진다" 는 예측은 이 모델로는 물어볼 수 없는 질문이었다. 다만
과대 계상 방향이라 +16.2% 는 **상한**이고, 결론은 그대로 선다.

**셋을 관통하는 것 하나.** 평탄 모델은 산술 대비 로드를 최대 32 배 과대 계상했다.
그래서 로드를 산술로 바꾸는 최적화(인덱스 버퍼)는 과소평가되고, 산술을 로드로
바꾸는 쪽(프리디케이션)은 과대평가됐다. 재기 전 예측이 이 프로젝트에서 여섯 번째로
틀렸고, 이번에는 **두 개가 같은 원인으로 반대 방향으로** 틀렸다.

## 검증

**안 변해야 하는 것.** `Flat` + 지연 0 에서 `render_bench.csv` 가 계속 바이트
단위로 같아야 한다. 새 모델은 **선택했을 때만** 켜진다. 이음매를 넣은 지금도
그렇다는 것을 확인했다.

**테스트가 옳은 이유로 통과하는지.** `DOC/12` 의 절차 그대로 — 고친 것을 다시
빼서 실패하는지 본다. 이번 건이면:

- coalescing 을 라인 수가 아니라 레인 수로 세면 실패하는가 — **인접·흩어짐·
  브로드캐스트 세 씬**이 필요했다. 브로드캐스트가 "주소를 센다" 와 "라인을 센다"
  를 갈라 준다. 셋 다 확인했다
- 캐시를 항상 히트로 만들면 실패하는가 — **같은 라인을 두 번 읽는 씬**이라야
  잡힌다. 한 번만 읽으면 히트가 없어서 통과한다
- 축출을 없애면 실패하는가 — **용량을 넘기는 씬** + **히트를 계층별로 세는 것**이
  둘 다 필요했다. `cache_hits` 하나로 세면 축출을 없애도 히트 수가 같다(전부 L1
  히트가 되므로). 두 계층이 존재하는 이유가 비용 차이인데 한 숫자로는 그것을
  측정할 수 없다 — 넷 중 셋이 이 이유로 안 잡혔다
- LRU 를 FIFO 로 바꾸면 실패하는가 — **선형 스윕으로는 안 잡힌다.** 둘 다 가장
  오래된 것을 버린다. L1 을 채우고 → 첫 라인을 다시 읽고 → 하나 더 읽어 넘치게
  하는 씬이라야 갈린다
- 지연을 0 으로 되돌리면 실패하는가 — **워프 둘 이상**이라야 잡힌다. 하나면
  가릴 상대가 없어서 지연이 있든 없든 같은 만큼 기다린다
