# 30 — `[a]` 스키닝 · `[v]` 애니메이션 구현 보고서
> **5단계가 닫혔다.** 계획서의 마지막 항목이다.
>
> **결과 한 줄**: 지어낸 데이터를 안 썼다. 실제 BVH 모션과 실제 리그로 검증하고,
> 저장소에는 **재배포 가능한 것만** 넣었다.

## 라이선스가 구현을 바꾼 이유

처음 계획은 "`.obj` 에 뼈가 없으니 스켈레톤을 지어낸다" 였다. 실제 리그
(mixamo, 과제물)를 쓸 수 있게 되어 확인해보니:

> Adobe: "really the only thing you can't do is **distribute the raw character and
> animation files**" — 금지 목록에 "Any type of free distribution" 이 명시.

**쓰는 것은 되고 저장소에 넣는 것은 안 된다.** 그래서:

| | |
|---|---|
| 저장소 기본값 | `assets/arm.bvh` (손으로 쓴 4관절 4프레임) + `assets/grid.obj`, 최근접 뼈 바인딩 |
| `--rig <dir> --motion <f>` | 실제 리그. 파일은 안 들어가고, 결론이 진짜 데이터에서 서는지 확인용 |

CMU Motion Capture Database 는 "may be copied, modified, or redistributed" 라
넣을 수 있다 — 파서가 아무 BVH 나 읽으므로 나중에 받아서 넣으면 그대로 돈다.

## 이름 충돌

이 저장소의 `gpurt/bvh.hpp` 는 **bounding volume hierarchy** 고, 모션 파일은
**Biovision Hierarchy** 다. 둘 다 그래픽스 층에 산다. 헤더를 `skeleton.hpp` 로
지었다 — **읽는 파일이 아니라 담는 것**으로 이름을 지어야 충돌이 안 난다.

## 데이터가 예측을 하나 더 깼다

계획서가 `[a]` 에 `V_SCALE_MAT4_F32` / `V_ADD_MAT4_F32` 를 예약해뒀다 (가중 합성용).
**둘 다 안 만들었다.**

실제 리그가 **삼각형 단위 강체 부착**이다 — 뼈마다 `.obj` 하나, 정점 풀은 공유,
면만 분할. 가중치가 **없다**. 지어낼 수는 있지만 지어낸 가중치 위의 측정은 실제
분할 위의 측정보다 약하다.

그리고 가중치가 있었어도 그 opcode 들은 졌다. 정점은 벡터 **하나**라:

```
행렬을 먼저 섞기 : 스케일 4×16 + 덧셈 3×16 + MATVEC 16 = 128
결과를 섞기      : MATVEC 4×16 + 스케일·덧셈 12       =  76
```

**합성은 같은 행렬이 벡터 4개 넘게 섬길 때만 이긴다** — `[i]` 의 교차점과 같은
`n > 4` 이고, 정점은 1 이다.

## 와이드 로드가 여기서 값을 한다

이웃 정점이 서로 다른 관절을 따르므로 **행렬 주소가 레인마다 다르다.** 상수 창이
못 하는 것이고, `V_LD_GLOBAL_MAT4_F32` 가 정확히 그 자리다. 정점당 5 명령:

```
bone   = load(bone_buffer + index*4)        스칼라 1
matrix = load_mat4(palette + bone*64)       와이드 1     ← 스칼라면 16
out    = matrix × (position, 1)             MATVEC 1
```

뼈 번호는 **셰이더가 직접 버퍼에서 읽는다** — `[shader]` 가 "any buffer it knows
the offset of" 를 이미 허용했고, varying 으로 나르면 패스 2 가 안 보는 숫자에
화면 정점 슬롯을 쓴다.

## 버그 셋

**1. 정렬을 빼먹었다.** 메시를 스케일만 하고 스켈레톤 안으로 **옮기지 않았다.**
78 관절 중 **3개**만 쓰였는데 — **프레임은 멀쩡히 움직였다.** 그래서 테스트가 보는
것은 "뭔가 움직였나" 가 아니라 **뼈 커버리지**다. 고치니 21개.

**2. 프레임을 안 지웠다.** `DepthUse::Test` 는 깊이 버퍼를 **읽지 소유하지 않는다.**
안 지우면 0 에서 시작해 **모든 프래그먼트를 거부**한다. 실패는 없고 프레임이 비고
발산이 0.00% 로 나온다 — 빈 프레임이 낼 값 그대로다. draw 경로는 프레임을 소유해서
지우고, 스테이지를 직접 모는 호출자는 자기가 해야 한다.

**3. 리그가 삼각형을 나누는데 정점을 나눈 줄 알았다.** `load_rig` 이 공유 정점 풀을
평탄 삼각형 목록처럼 넘겼다. **내내 뭔가를 그리고 있었다** — 25,342 삼각형에 walk 이라
런이 안 끝나서 프레임을 본 적이 없었기 때문이다. 이음매 정점은 삼각형 둘을 통해 뼈
둘에 속하고, 평탄화하면 각 복사본이 **자기 삼각형의 뼈**를 받는다.

## walk 이 캐릭터를 못 나른다

| | 25,342 삼각형, 64×32 |
|---|---:|
| `draw_walk` | **124초 / 프레임** |
| BVH 레이 트레이서 | **3.1초 / 프레임** |

walk 은 정의상 픽셀×삼각형이라 이건 결함이 아니라 `[g1]` 이 존재하는 이유다.
저장소에서 그걸 **느낄 만큼 큰 첫 메시**일 뿐이다.

**트리도 값을 받아간다**: 레이 트레이서는 정점 스테이지가 없어서 스키닝된 메시가
**이미 포즈된 채로** 와야 한다. `--route raytrace` 에서는 스키닝이 호스트로 가고
장치는 순회만 한다. 경로의 성질이지 구멍이 아니라 그렇게 적었다.

실제 리그 전체: **147,336 정점 / 49,112 삼각형 / 58 프레임을 4분**, 발산 88%.

## GIF 을 직접 썼다

`gpurt` 의 서드파티 의존성이 0 이고, 애니메이션 뷰어는 첫 의존성을 들일 이유로
약하다. LZW 약 100줄 + 헤더·팔레트·블록 스트림.

팔레트는 **고정 216색 큐브**다. 적응형 양자화기는 **틀릴 수 있는 알고리즘이 하나 더**
생기는 것이고, 이 프레임들은 검은 바탕 위의 부드러운 셰이딩이다.

**검증은 포맷에서 따로 쓴 디코더로 한다.** 인코더를 자기 역함수에 대보면 아무리
틀려도 자기랑은 맞는다. 두 경우: 긴 런과 매 픽셀 바뀌는 구간을 한 프레임에 (인코더는
둘 중 하나만 틀릴 수 있다), 그리고 **사전을 채울 만큼 긴 것** — 비우지 않고 추가만
멈춘 인코더도 디코드되는 파일을 낸다. 그래서 크기가 아니라 픽셀을 본다.
