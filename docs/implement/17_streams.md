# 17 — `[m4b]` 스트림 + indirect launch 구현 보고서
> 커밋: `a6ae06b` 스트림 · `5040933` indirect · `5670339` 벤치 · `489484f` 문서

> `DOC/16` 이 SM 을 여러 개 만들었다. 이 문서는 그 위에 **큐**를 얹은 것 —
> 커널 둘이 동시에 기계에 올라가는 첫 지점이고, `[m4]` 가 닫힌다.

## 왜 이것이 `[m4]` 의 어려운 절반이었나

초기 설계 기록 가 이렇게 적어뒀다.

> **쉬운 절반.** 런치를 큐에 넣고 `myrt_sync` 가 드레인하는 것은 지금 구조로도
> 된다 — `kernel(args)` 가 런치 시점에 `Program` 을 만드므로 `args` 가 죽어도 된다.
>
> **어려운 절반.** 그렇게 해도 **겹칠 것이 없다.** … **통계가 진짜 문제다.**
> 스트림 둘이 겹쳐 돌면 `divergence_rate()` 가 둘을 섞고, `elapsed_seconds_` 는
> 이중 계산이 된다.

`[m4a]` 가 첫 문제를 없앴다 — SM 이 여럿이면 겹칠 곳이 생긴다. 남은 것이 통계였고,
답은 **일을 나누는 것과 시간을 나누는 것을 다르게 취급하는 것**이었다.

---

## 1. 스케줄러 — 큐를 여럿 받는 상주 루프

```cpp
struct GridLaunch {
    const Program* program;
    NextBlock next_block;
    size_t shared_bytes;
    uint32_t stream;      // 같은 값끼리는 순서, 다른 값끼리는 자유
};

void run_streams(const std::vector<GridLaunch>&, DeviceSpan,
                 std::vector<SchedulerStats>* per_launch = nullptr);
```

`run_grid` 은 이제 **원소 하나짜리 `run_streams`** 다. 루프 본체는 거의 안 바뀌었다 —
SM 이 슬롯을 채울 때 "그리드" 대신 "**아직 줄 수 있는 런치들**" 에서 고를 뿐이다.

### 순서 규칙

```cpp
stream_clear(i) = 나보다 앞에 선언된 같은 stream 의 런치가 전부 finished
finished        = 더 줄 블록이 없고(exhausted) && 상주 0 && 미배치 블록 없음
```

**끝난 것이 아니라 "완전히 은퇴한 것"** 을 본다. 블록을 다 나눠줬어도 아직 돌고
있으면 다음 런치는 못 들어간다 — 그게 스트림이 보장하는 것이다.

### 잔여 자원 계산이 바뀌었다

전에는 첫 블록이 `residency()` 를 정하고 SM 마다 `per_sm` 개를 넣었다. 커널이 둘이면
블록이 서로 안 닮았으므로 그 숫자가 존재하지 않는다. 그래서 **한 블록씩 재는 형태**로
바꿨다.

```cpp
fits(unit, i) = unit 이 비었거나
              ( 슬롯 수  < blocks_per_sm
             && 워프 합  + p.warps         <= warp_slots_per_sm
             && 공유 합  + shared_bytes    <= shared_bytes_per_sm )
```

균질한 그리드에서는 `residency()` 와 **정확히 같은 수**가 나온다(그래서 기존 표가
안 흔들렸다). 빈 SM 은 무조건 받는다 — 기계보다 큰 블록도 혼자서는 돌아야 한다.

### 블록을 **먼저 만들어 보고** 넣는다

워프 수를 알아야 자리에 맞는지 아는데, 워프 수는 블록을 만들어야 안다. 그래서 런치마다
`peeked` 를 하나 들고 있는다 — 만들었지만 아직 자리가 없는 블록. 안 맞으면 버리지 않고
**다음 기회에 쓴다.** `next_block` 이 한 번 더 불리면 그 블록은 영영 사라진다.

---

## 2. 통계 — 나뉘는 것과 겹치는 것

이것이 이 단계의 핵심 판단이다.

| | 무엇 | 합치면 |
|---|---|---|
| **일** | `warp_steps`, 레인 수, 캐시 카운터 | 총합과 **정확히 같다** |
| **시간** | `cycles`, `stall_steps` | 총합보다 **크다** |

일은 발행한 워프의 주인에게 간다. `step_warp` 앞뒤로 구조체를 통째로 스냅샷해서 차를
더한다 — 필드를 나열하면 나중에 추가된 카운터가 빠지기 때문에 `operator-=` 를 만들었다.

시간은 **그 사이클에 상주해 있던 모든 런치에게 각각** 물린다. 스트림 둘이 같은 사이클을
같이 봤으면 둘 다 그 사이클을 산 것이고, 나누면 거짓이 된다.

```
겹침 = Σ(스트림별 cycles) − 전체 cycles
```

이 잉여가 **겹친 양 그 자체**다. 재는 것이 목적이었으니 숨기지 않고 그대로 둔다.
(`OverlappingStreamsAreBothChargedForTheCyclesTheyShared`)

**비용은 안 낸다.** `per_launch` 가 `nullptr` 이면 스냅샷을 안 뜬다. 런타임은 큐에
런치가 둘 이상일 때만 넘기므로, **기존 경로는 명령 하나도 안 늘었다.**

---

## 3. 런타임 — 큐, 그리고 읽을 틈

```cpp
StreamId myrt_stream_create();
void myrt_launch_async   (kernel, LaunchConfig,         args, stream);
void myrt_launch_indirect(kernel, IndirectLaunchConfig, args, stream);
void myrt_wait();                       // 돌리기만
void myrt_sync(report);                 // 돌리고, 찍고, 지운다
const SchedulerStats& myrt_stream_stats(StreamId) const;
```

**`myrt_wait` 가 새로 필요했던 이유.** `myrt_sync` 는 통계를 **지운다.** 동기 런치는
`myrt_launch` 가 반환한 뒤에 읽으면 됐지만, 비동기는 sync 전에 아무것도 안 돈다 —
"돌리는 것" 과 "지우는 것" 이 한 함수에 묶여 있으면 읽을 틈이 없다. 그래서 갈랐다.
`Runtime.SyncResetsStats` 가 계약으로 남아 있고, 그 계약을 안 건드린다.

**`myrt_launch` 는 큐에 넣고 즉시 드레인한다.** 대기 중이던 다른 스트림도 같이 나간다 —
"런치가 반환했다" 가 "기계가 비었다" 를 뜻하지 않으면 동기가 아니다.

**args 는 죽어도 된다.** `kernel(args)` 를 enqueue 시점에 부른다. `Program` 이 상수를
전부 굽고 있으므로 자기완결적이다. 살아 있어야 하는 것은 프로그램이 주소로 가리키는
**장치 메모리**뿐이다.

### indirect launch

```cpp
struct IndirectLaunchConfig { size_t grid_offset; dim3 block; size_t shared_bytes; };
```

grid 를 장치 메모리의 **연속된 float 셋**에서 읽는다. 읽는 시점이 전부다 — enqueue 가
아니라 **그 런치가 기계에 도달할 때**, 즉 같은 스트림의 앞 런치가 은퇴한 뒤다. 그래서
앞 커널이 쓴 값을 뒤 런치가 grid 로 쓴다.

float 인 이유는 ISA 에 정수 레지스터가 없어서고, 2²⁴ 까지 정확하다. `decode_address`
를 그대로 통과시킨다 — 커널이 쓴 규칙으로 읽는다.

**빈 grid 는 에러가 아니다.** `LaunchConfig` 에서는 던지지만 여기서는 정상이다.
"그릴 것이 없다" 는 컬링 패스가 도달할 자격이 있는 결론이고, 그걸 거부하면 호스트가
방금 장치에 시킨 판단을 자기가 다시 확인해야 한다.

## 4. 같이 고친 스케줄러 규칙 둘

둘 다 스트림이 드러냈지만, 스트림 없이도 틀린 것이었다.

### ① 시계가 방금 도착한 블록을 건너뛰지 않는다

```cpp
if (!loaded_any && soonest != UINT64_MAX && soonest > now) { now = soonest; }
//  ^^^^^^^^^^^ 새로 붙은 조건
```

이번 사이클에 슬롯이 새 블록을 받았으면 점프하지 않는다. 전에는 SM 의 다른 워프들이
기다리는 중이면 그 시각까지 뛰었고, 방금 들어온(즉시 발행 가능한) 블록이 그 공백을
통째로 앉아서 보냈다. 두 번째 스트림의 블록이 첫 스트림이 멈춘 SM 에 들어가면
**상관없는 커널의 대기를 대신 기다리게** 된다.

### ② breadth-first 가 빈 기계에서 시작한다

옛 코드는 첫 블록을 `fill_all()` **밖에서** `units[0]` 에 밀어 넣었다 — 그 블록이
`residency()` 를 정해야 했기 때문이다. 그래서 fill 의 첫 바퀴가 **`units[0]` 에 두
번째 블록을 주고 나서** `units[1]` 에 첫 번째를 줬다.

```
옛것   SM0: ●●   SM1: ●   …   SM62: ●   SM63: (비어 있음)
새것   SM0: ●    SM1: ●   …   SM62: ●   SM63: ●
```

64 블록을 64 SM 에 뿌리면 **마지막 SM 이 놀고 첫 SM 이 둘을 든다.** 잔여 자원을 한
블록씩 재게 되면서 그 프롤로그가 통째로 사라졌고, off-by-one 도 같이 사라졌다.

`DOC/16` 이 "greedy 로 채우면 80x, 흩으면 250x" 를 적었는데, 흩는 쪽에도 머리 하나가
어긋나 있었던 셈이다.

### 무엇이 얼마나 움직였나

| | 전 | 후 | 어느 규칙 |
|---|---:|---:|---|
| 1 SM, 8 블록 | 76,490 | 76,484 | 시계 |
| 8 SM, 1 블록 | 71,998 | 71,982 | 시계 |
| 16 SM, 8 블록 | 9,446 | **9,347** | fill |
| 32 SM, 8 블록 | 9,967 | **9,593** | fill |
| 1 SM, 2 블록 | 283,962 | 284,185 | 시계 |

**세 규칙을 따로 빌드해서 갈랐다** — 옛 루프 + 시계 수정, 새 루프 - 시계 수정, 둘 다.
어느 행이 어느 규칙 때문인지는 추측이 아니라 그 세 판의 차다.

기본 기계(1 SM × 1 블록)는 둘 다 도달 불가라 `render_bench` · `cache_bench` ·
`model_bench` 가 **바이트 동일**하다. 마지막 행이 반대 방향인 것은, 일찍 발행하면 어느
워프가 라인에 먼저 닿는지가 바뀌고 캐시는 두 번째 물음에 더 싸게 답하기 때문이다.

## 나온 것 — `test/benchmark/src/stream_bench`

### ① 그리드가 못 채우는 기계 (8 블록, 8 SM)

| 런치 | 블록/런치 | 한 스트림 | n 스트림 | 배속 |
|---:|---:|---:|---:|---:|
| 1 | 8 | 90 | 90 | 1.00x |
| 8 | 1 | 720 | 90 | **8.00x** |

첫 행이 대조군이다 — 이미 꽉 찬 그리드는 두 번째 큐가 **놓을 자리가 없다.** 아래로
갈수록 같은 일을 좁은 문으로 밀어 넣는 것이고, 동시성이 문을 다시 연다.

### ② 서로의 대기를 가린다 (1 SM, 2 블록)

| 첫 | 둘 | 첫 단독 | 둘 단독 | 한 스트림 | 두 스트림 | 가려진 양 |
|---|---|---:|---:|---:|---:|---:|
| memory | memory | 6,490 | 6,490 | 12,980 | 6,492 | **99.97%** |
| memory | compute | 6,490 | 90 | 6,580 | 6,490 | **100.00%** |

**메모리 커널 둘이 하나 값이다.** 400 사이클 기다리는 워프는 뒤에 399 개의 발행 슬롯을
남기고, 두 번째 커널은 22 개를 원한다.

**그런데 통설의 형태와는 다르다.** "메모리 바운드와 컴퓨트 바운드를 짝지어라" 가
스트림의 상투적 조언인데, 여기서는 **memory + memory 도 똑같이 다 가린다.** 기전이
유휴 발행 슬롯이지 상보적인 유닛이 아니기 때문이다 — 이 기계에는 나눌 유닛이 없다.
로드 파이프와 산술 파이프가 갈린 기계라면 두 행이 갈릴 것이고, **이 기계는 그걸 못
잰다.** 한계로 적는다.

### ③ 호스트가 모르는 grid

| 보이는 수 | grid | indirect 발행 | 사이클 | host 발행 | 사이클 |
|---:|---:|---:|---:|---:|---:|
| 8 | 8 | 6,924 | 900 | 6,688 | 90 |
| 0 | 0 | 236 | 810 | 0 | 0 |

**메모리에서 grid 를 읽는 것 자체는 0 이다.** 행마다 차이가 정확히 236 이고, 마지막
행이 236 의 정체를 말한다 — 아무것도 결정하지 않은 컬링 패스 그 자체. indirect 런치는
레인 연산을 **하나도** 안 더한다.

**드는 것은 직렬 패스다.** 900 중 810 이 컬링이고, 그건 이 ISA 에 레인을 합칠 atomic 이
없어서 한 스레드가 여덟 개를 걸어간 결과다. 모양은 맞지만 구현은 가장 느린 형태다.

## 검증

- `ctest` **298/298** (`test_streams` 15 개 신규)
- **일은 나뉘고 시간은 겹친다** — 두 성질을 각각 테스트가 잡는다
  (`WorkCountersPartitionAcrossStreams`, `AStreamIsChargedWhatItWouldHaveCostAlone`,
  `OverlappingStreamsAreBothChargedForTheCyclesTheyShared`)
- **순서** — 같은 스트림의 뒤 런치가 앞 런치의 출력을 읽어 정확히 2.0 을 본다
- **indirect** — 앞 커널이 쓴 grid 로 돈다 / 빈 grid 는 아무것도 안 돈다 /
  정수가 아니면 던진다 / 장치 메모리 밖이면 던진다
- `render_bench` · `cache_bench` **바이트 동일**
