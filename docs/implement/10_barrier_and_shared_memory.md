# 10단계 — BARRIER와 공유 메모리

> **상태: 구현 완료.** `ctest` 184/184. 계획과 달라진 부분은 아래 "구현 결과"
> 절에 정리했다.

## 목표

`__syncthreads()`를 만든다. 그리고 그것으로 타일의 삼각형을 공유 메모리에
한 번만 올려 재사용한다.

```
지금    타일 안 256개 스레드가 같은 18개 float를 각자 전역에서 읽는다
목표    블록이 한 번 읽어 shared에 두고, 전원이 거기서 읽는다
```

---

## 왜 이걸 하는가

### [1] 남은 비용의 95%가 로드다

9단계 `[5b]` 타일드 커널의 루프 본문을 **워프 하나·삼각형 하나** 기준으로 뜯으면:

| 항목 | 계산 | 비용 |
|------|------|------|
| 전역 로드 9개 | 9 × 32레인 × 100 | **28,800** |
| 나머지 산술 | 약 37 명령어 × 32 × ~1.3 | 1,540 |

`V_LD_SHARED_F32`는 비용 8이다. **로드를 옮기면 전체의 약 85%가 더 빠진다** —
binning이 84% 줄인 위에서 한 번 더.

### [2] 놀고 있는 부품이 정확히 이것이다

```
ThreadBlock::shared_mem   4096 floats   ← 아무도 안 씀
V_LD_SHARED_F32           구현·테스트됨  ← 아무도 안 씀
V_ST_SHARED_F32           구현·테스트됨  ← 아무도 안 씀
```

3단계에서 만들고 5단계까지 아무 커널도 건드리지 않았다. 공유 메모리를 쓰는
커널이 없다는 것은 **"메모리 계층을 모델링했다"는 주장에 빈 곳이 있다**는 뜻이다.

### [3] 포트폴리오에서 이게 제일 값이 크다

성능만 보면 배리어 없이도 8.8배를 얻는다(아래 D안). 배리어의 추가 이득은 35%다.

그럼에도 A안을 고른 이유는 **스케줄러 기능**이라는 점이다. 이 프로젝트의 핵심이
워프 스케줄러고, `__syncthreads()`는 GPU 관련 면접에서 가장 자주 나오는 개념 중
하나다. 그리고 뒤에 나올 **발산 하의 교착**은 이 프로젝트가 이미 가진 divergence
모델 위에서만 보일 수 있다.

---

## 선택지 비교 (기록)

배리어를 피하는 길도 있었다. 남겨두는 이유는 나중에 "왜 굳이 배리어를"이라는
질문이 다시 올 때 답이 되기 때문이다.

| | ISA 변경 | 타일 모양 | 삼각형당·워프당 | 대비 |
|---|---|---|---|---:|
| **A. BARRIER** | 새 opcode + 스케줄러 | 32×8 자유 | ~2,425 | **11.9×** |
| B. 블록 = 워프 1개 | 없음 | 32×1 고정 | ~3,276 | 8.8× |
| D. 워프별 전용 슬라이스 | 없음 | 32×8 자유 | ~3,276 | 8.8× |

현재 28,800 기준.

**B와 D가 배리어를 피할 수 있는 이유**: 한 워프의 32 레인은 같은 명령어를 나란히
실행하므로, "store 명령어가 load 명령어보다 앞에 있다"는 프로그램 순서만으로
가시성이 보장된다. 워프 간 합의가 없으면 동기화도 필요 없다.

- **B**는 타일을 32×1로 줄여 블록을 한 워프로 만든다. 간단하지만 타일이 얇아
  8행에 걸친 삼각형이 8개 타일에 중복 배정된다.
- **D**는 타일을 유지하고 워프마다 shared의 자기 구역을 채운다. 8개 복사본이
  생기지만 레인 간 32배 중복은 사라진다.
- **A**만 블록 전체가 한 번 채우고 공유한다. 채우기 비용이 D의 1/8.

## 설계

### ISA

```cpp
BARRIER,  // wait for every live warp of the block   (all operands unused)
```

**`RET` 앞에 넣는다.** `test/unit/test_isa.cpp`의 `OPCODE_COUNT`가
`static_cast<int>(Opcode::RET) + 1`로 정의돼 있어 RET이 마지막이어야 한다.
`BRA`(21) 등 기존 경계 검사는 그대로 유지되고, `BARRIER`가 23, `RET`이 24가 된다.

**네이밍**: 워프 상태만 바꾸므로 접두사도 타입 접미사도 없다 — `BRA`/`RET`과 같은
제어 흐름 그룹이다. `test/unit/test_isa.cpp`의 `is_control_flow`에 추가해 기계 검증한다.

**비용은 1.** 배리어의 진짜 비용은 명령어가 아니라 **스톨**이고, 그건 다음 절의
한계 항목이다.

### 스케줄러 — 세 지점

**[1] `step_warp`가 레인 루프 *위에서* 가로챈다.**

배리어는 워프 상태라 `execute(Thread&)`로는 표현이 안 된다. 지금까지 모든 opcode가
레인별로 처리됐으므로 **구조상 처음 갈라지는 지점**이다.

```
step_warp
  min_pc 계산 → active_mask 구성
  if (program[pc].op == BARRIER) { ... return false; }   ← 새로 생기는 분기
  for lane: execute(...)
```

`execute`의 switch에도 `case BARRIER:`를 두되 **throw** 한다. `-Wswitch` 안전망은
유지하면서 "여기 오면 안 된다"를 침묵이 아니라 예외로 말하게 한다.

**[2] `Warp::at_barrier`**

```cpp
struct Warp {
    ...
    bool at_barrier = false;
};
```

기다리는 워프는 큐에서 완전히 빠진다. 대기 비용이 "돌아오지 않는 턴"으로만
나타나는 것이 이 모델의 특징이다.

**[3] `run()`의 큐 고갈 처리**

```cpp
while (!ready_queue_.empty()) {
    ... step_warp ...
    if (ready_queue_.empty() && release_barrier(block)) {
        continue;
    }
}
```

**큐가 비었다는 것 자체가 도착 판정이다.** 아무도 턴을 못 쓰는데 누군가 기다리고
있다면, 일이 남은 워프는 전부 배리어에 도달했다는 뜻이다. 별도의 도착 카운터가
필요 없다.

### 발산 하의 배리어 — 이 단계의 핵심

```
if (조건) {
    BARRIER;      ← 일부 레인만 도달
}
```

min-PC 발행이라 워프는 **도달한 레인만 켜진 채로** 배리어를 만난다. 나머지는
분기로 건너뛰어 더 높은 pc에 있다. 그대로 기다리면 **절대 오지 않을 스레드를
기다리며 동기화한 것**이 된다.

```
active_lane_count(warp) < 아직 살아 있는 스레드 수  →  예외
```

CUDA는 배리어를 감싸는 조건이 블록 전체에서 동일하게 평가될 것을 요구하고, 그렇지
않으면 **멈추거나 조용히 틀릴 수 있다**고 문서에 적어둔다. 여기서는 즉시 던진다.
(특정 아키텍처가 어떻게 실패하는지는 확인하지 못했으므로 단정하지 않는다.)
하드웨어 규칙이 왜 존재하는지
시뮬레이터로 보이는 것이 이 단계에서 성능 다음으로 큰 산출물이다.

### 은퇴한 워프는 기다리지 않는다

배리어 전에 끝난 워프를 계속 기다리면 교착이다. 현재 하드웨어가 "종료한 스레드는
도착한 것으로 친다"로 처리하고, 디버깅 가능한 시뮬레이터에도 그게 맞다.

부분 블록에서 처음부터 전 레인이 비활성인 워프가 생길 수 있다는 실제 사정도 있다
(`myrt_launch`가 `threads_per_block`을 넘는 스레드를 비활성화한다).

## 공유 메모리 타일 커널

### 적재

```
tile_count 개 삼각형 = 9 × count float

lane_in_block = (thread_y - block_y * TILE_HEIGHT) * TILE_WIDTH
              + (thread_x - block_x * TILE_WIDTH)

for (i = lane_in_block; i < 9 * count; i += 256)
    shared[i] = global[tri_addr + i * 4]

BARRIER
```

256 스레드가 나눠 읽으므로 삼각형 28개까지는 반복 1회로 끝난다
(`9 × 28 = 252 < 256`).

블록 좌표를 빼서 블록 안 인덱스를 만드는 것에 주의 — `thread_x`는 **전역** 좌표다.

### 읽기

루프 본문의 전역 로드 9개가 그대로 shared 로드 9개가 된다. 주소는
`shared_base + i * 36`으로, 전역 버전과 형태가 같다.

### 공유 메모리 예산

```
4096 float / 9 = 삼각형 455개
```

한 타일에 그보다 많으면 넘친다. `[7]`에서 **초과 시 예외**로 끊는다 — 조용히
덮어쓰면 다른 타일의 데이터를 읽게 되고, 그건 추적이 불가능하다.

실제 하드웨어도 같은 문제를 갖는다. 타일에 프리미티브가 너무 많으면 여러 패스로
나눈다(PowerVR의 parameter buffer overflow). 여기서는 범위 밖.

## 설계 결정 및 이유

**BSP 모델 쪽에 선 것**
: 원자적 연산 방식은 세밀한 동기화·경합·예측 불가능한 비용을, 배리어 방식은 굵은
  집합 지점과 예측 가능한 비용을 준다. 배경은
  [ref_bulk_synchronous.md](ref_bulk_synchronous.md) 참고 — 우리 통계가 BSP 비용
  모델의 `l`(배리어 대기)을 0으로 본다는 한계도 거기 정리해뒀다.

**A안(배리어)을 고른 것**
: 성능 이득은 D안 대비 35%뿐이다. 고른 이유는 스케줄러 기능이라는 점, 그리고
  발산 하의 교착이 이 프로젝트에서만 보일 수 있는 것이라는 점.

**`BARRIER`를 `RET` 앞에 넣는 것**
: `OPCODE_COUNT`가 `RET + 1`로 정의돼 있다. RET을 마지막으로 유지하면 기존 경계
  검사가 전부 살아남는다.

**`execute`에서 throw 하는 것**
: 도달 불가능한 분기를 `break`로 두면 나중에 누가 `step_warp`의 가로채기를 지웠을 때
  **조용히 no-op**이 된다. 예외면 첫 테스트에서 잡힌다.

**큐 고갈을 도착 판정으로 쓰는 것**
: 별도 카운터를 두면 워프 은퇴와 동기화해야 하고, 그 둘이 어긋나는 것이 정확히
  교착 버그의 형태다. 큐는 이미 그 정보를 갖고 있다.

**발산 검사를 예외로 두는 것**
: 하드웨어는 조용히 틀린다. 시뮬레이터가 하드웨어를 그대로 흉내 낼 이유는 없고,
  **규칙이 있다는 사실 자체를 보이는 것**이 목적이다.

## 구현 결과

### [+] 빌더에 공유 메모리 호출이 아예 없었다

`load` / `store` / `load_into` 가 전부 전역이고, `V_LD_SHARED_F32` /
`V_ST_SHARED_F32` 는 ISA 와 스케줄러에만 있었다. 3단계에서 만들고 아무도 안
쓴 opcode 라 빌더가 손잡이를 기를 이유가 없었던 것이다.

`load_shared` / `store_shared` 를 추가했다. `load` 가 암묵적으로 전역인
비대칭이 남는데, 고치려면 모든 커널의 호출부를 건드려야 해서 이 변경에 섞지
않았다.

### [!] 공유 메모리 주소는 **바이트**다

이 문서가 처음에 "`V_LD_SHARED_F32` 는 float 인덱스로 주소를 잡는다"고 적었는데
틀렸다. `gpurt/scheduler.cpp` 가 `decode_address` 를 거쳐 바이트로 다룬다 —
전역과 동일하다.

덕분에 `[e]` 가 단순해졌다: 같은 오프셋 숫자에 `load` → `load_shared` 치환뿐.

### [+] 적재 루프는 회전시켜야 한다

`k.if_` 로 본문을 감싸면 **일이 없는 레인도 루프에 한 번 들어간다.** 삼각형
2개짜리 타일이면 `staged = 18` 인데 레인은 256개라 238개가 헛돌고, 그 헛도는
반복이 `global[tri_addr + lane*4]` 를 읽어 **버퍼 밖 접근으로 예외**가 날 수
있다.

앞에서 빼내는 형태(pre-test)로 바꿨다. 레인마다 반복 횟수가 다른 것은 min-PC
가 알아서 처리하고, 전원이 `fill_done` 에 모인 뒤 배리어를 만난다.

### [−] divergence 예측이 빗나갔다

`[5]`, `[5b]` 에서 "비용이 줄면 divergence 수치는 오른다"를 관찰하고 여기서도
오를 것이라 적어뒀는데 **평평했다** (2.1% → 2.0%).

이유: `divergence_rate` 는 `masked_lane_slots / lane_slots` 이고 둘 다
`warp_steps` 기반이다. **`instruction_cost` 로 가중되지 않으므로 비용을 보지
못한다.** binning 은 *반복 자체*와 그 마스크를 없앴으니 수치가 움직였고,
staging 은 명령어 값만 싸게 만들 뿐 마스크는 하나도 안 바꾼다.

앞선 관찰은 자기 원인에 대해서는 맞았지만 규칙으로는 틀렸다. 정정을
`test/benchmark/src/RESULTS.md` 에 적었다.

### [=] 맞았던 것

배리어 위치가 이 커널의 유일한 함정이라는 예상은 맞았고, 발산 검사가 실제로
그것을 잡는다. 가장자리 블록(50×20 프레임)에서 화면 밖 스레드가 배리어를
건너뛰면 런치가 거부된다 — `SharedRasterSurvivesAFrameThatDoesNotFillItsTiles`
가 그 경우다. 기본 64×32 는 32·8 의 배수라 이 경우가 아예 안 생겨서, 크기를
일부러 어긋나게 한 테스트가 따로 필요했다.
