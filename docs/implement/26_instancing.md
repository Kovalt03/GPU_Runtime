# 26 — `[i]` 인스턴싱 구현 보고서
> **4단계의 첫 항목.** `[g2]` TLAS 와 `[m7]` 완결이 이것을 딛는다.
>
> **결과 한 줄**: 계획서가 적어둔 교차점 예측(정점 4개)이 **두 자릿수 틀렸다**.
> 실제는 96~128 이고, 틀린 이유가 이 항목에서 가장 값진 부분이다.

## 블록 하나가 인스턴스 하나 — 그래서 상수 창을 탄다

```
패스 1 launch:  block {32,1,1}   grid {ceil(V/32), instances, 1}
                                              ↑ block_y() = 인스턴스
```

grid 를 **둘째 차원으로 늘렸다.** 첫째를 길게 하면 인스턴스가 워프 안에서 섞이는데,
그러면 인스턴스 행렬이 레인마다 달라진다. 둘째 차원으로 두면 **한 블록이 한
인스턴스**고, 행렬이 워프 유니폼이다.

그게 상수 창의 전제다. `gpurt/scheduler.cpp` 가 창을 **워프당 한 번** 과금하는 근거는
"addressed from the register the launch seeded, so the address is the same in
every lane **by construction**" 인데, 여기에 `block_y` 를 더해도 **워프가 블록 안에
살므로** 유니폼이 유지된다. 근거를 어기는 것이 아니라 **확장**하는 것이고, 실제
상수 캐시가 유니폼 주소에 브로드캐스트하는 것과 같다.

**결과: 인스턴스 행렬 배달이 워프당 1회.** 이게 나중에 예측을 뒤집는다.

## 정점 버퍼는 인스턴스-major

화면 정점을 `[instance][vertex]` 로 두면 패스 2 는 **같은 stride 의 더 긴 목록**
하나를 볼 뿐이다. 래스터 세 경로도 클리핑도 **한 줄도 안 고쳤다.**

## `V_MATMUL_MAT4_F32` — 두 번째 예약 슬롯

비용 64 (4×4×4 MAC). MATVEC 이 16 (4×4) 인 것과 같은 근거다. `V_MATVEC_MAT4_F32` 가
정점 스테이지 때 첫 슬롯을 채웠고, 이게 둘째다 — **이름을 안 고치고 자리만 채웠다.**

`test_scheduler` 가 항등식을 잡는다: `MATMUL(VP,M)` 뒤 `MATVEC` 한 번이 `MATVEC` 두
번과 같은 자리에 떨어진다. 두 행렬은 대칭도 아니고 교환도 안 되게 골라서 피연산자
순서 실수가 상쇄되지 않는다.

## 예측이 왜 틀렸나 — 이 항목의 본론

초기 설계 기록 에 **재기 전에** 이렇게 적혀 있었다:

> `V_MATMUL_MAT4_F32`. **합성 대 두 번 적용의 교차점** n>4

산술은 맞다. 합성 = `64n + 16Vn`, 두 번 적용 = `32Vn`, 교차 `V > 4`. 잰 것:

| 인스턴스당 정점 | per-vertex | composed | 합성 |
|---:|---:|---:|---:|
| 8 | 105,216 | 154,080 | **+46.4%** |
| 32 | 400,896 | 437,472 | +9.1% |
| 64 | 801,792 | 821,984 | +2.5% |
| 96 | 1,202,688 | 1,206,496 | +0.3% |
| **128** | 1,603,584 | 1,591,008 | **−0.8%** |
| 256 | 3,207,168 | 3,129,056 | −2.4% |
| 512 | 6,414,336 | 6,205,152 | −3.3% |

**교차점이 96~128.** 예측의 24~32배다.

### 이유 둘

**1. 합성 패스가 쓰는 것은 곱이 아니다.** 스레드 하나가 float 16 개를 읽고 16 개를
쓴다. `instruction_cost(V_LD_GLOBAL_F32) = 100` 이므로 **32 × 100 = 3,200**, 그
가운데 MATMUL 은 **64**. 예측이 센 산술은 패스가 쓰는 것의 **2%** 다.

**2. 패스 1 은 행렬 값을 안 낸다.** 상수 창이 워프당 한 번이라, per-vertex 갈래는
모델 행렬을 **공짜로** 받고 여분의 MATVEC 만 낸다. composed 갈래는 **행렬 하나를
메모리로 실어 날라야** 한다.

**그래서 실제 거래는 "곱 하나 대 곱 넷" 이 아니라 "정점당 MATVEC 하나 대 메모리를
통과하는 행렬 하나" 다.** 상수 창(`[u]`)을 만든 것이 이 항목의 답을 바꿨고, 그건
`[u]` 를 할 때 예상한 파급이 아니다.

**교정 지렛대라고 적었던 것이 아니었다.** `V_LD_GLOBAL_MAT4_F32` 을 만들면 교차점이
산술이 말한 자리로 돌아간다고 여기 적었는데, **만들어서 재보니 표가 한 자리도 안
움직였다.**

그럴 수밖에 없었고 규칙은 이미 VEC3 에 적혀 있었다 — **Flat 은 레인당 float 로 매기니
와이드 로드는 정확히 그 부품들이다.** 사는 것은 **요청한 라인 수**이고 그건
`Coalesced` 만 센다. 이 표는 전부 Flat 이다.

`Coalesced` 에서는 제값을 한다: 레인 16 개가 각자 행렬을 읽는 것이 스칼라 16 번이면
27,296, 와이드 한 번이면 3,296 (**−87.9%**), 합성 패스가 79,616 → 30,016.
**이 표의 교차점은 비용 모델의 성질이지 ISA 의 성질이 아니다.**

## 검증

**두 갈래가 같은 프레임을 낸다** — 다만 `ASSERT_EQ` 가 아니라 `ASSERT_NEAR` 다.
부동소수 행렬 곱은 **결합법칙이 성립하지 않아서** `(VP·M)·v` 와 `VP·(M·v)` 가 몇 ulp
어긋난다. BVH(`DOC/25`)가 EQ 였던 것과 갈리는 지점이고, 처음에 EQ 로 썼다가 실패해서
알았다.

무해하지 않다 — 정점이 픽셀 중심 한 끗 차로 넘어가면 커버리지가 바뀐다. 그래서
**덮인 픽셀 집합이 완전히 같은지**를 따로 센다(0 이어야 한다).

그리고 **인스턴스가 자기 행렬 자리에 그려지는지**를 잡는다. 하나를 원점에, 넷을
흩어서 그린 뒤 넷에만 켜진 픽셀이 있어야 한다 — 없으면 전부 겹쳐 그린 것이다.
항등 인스턴스 하나짜리 draw 가 uninstanced draw 와 픽셀 단위로 같은 것도 함께.

## 버그 둘

**1. 상수 창이 인스턴스 행렬을 가리키는데 VP 도 거기서 읽었다.** per-vertex 갈래가
`uniform_offset != 0` 이면 창에서 VP 를 읽는 기존 경로를 탔는데, 창 base 를
인스턴스 행렬로 옮겨놨으니 **모델 행렬을 두 번 적용**했다. 인스턴스가 엉뚱한 자리에
그려졌다. 고침: 인스턴스일 때 VP 는 무조건 굽는다 — 창은 **변하는 것**에 쓴다.

**2. `instance_count == 1` 이면 인스턴스 행렬을 무시했다.** 조건을 개수(`> 1`)로
썼는데, 인스턴스 하나짜리 draw 도 변환은 있다. 조건을 **행렬이 왔는가**
(`instance_offset != 0`)로 바꿨다. 이게 uninstanced 커널을 그대로 두는 조건이기도
하다.
